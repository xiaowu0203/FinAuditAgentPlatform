# P3.5 RBAC 权限体系与部门实体 · 执行点文档

> 版本: v0.1（草案待确认） ｜ 状态: **规划中，未开工** ｜ 前置依赖: P3 已合并
> 目标: 三块并进——① 轻量资源级 RBAC（权限资源 + 统一鉴权组件，堵住管理接口提权洞）；② 部门实体（完整树形，`dept_name` 字符串退役为快照/显示）；③ 管理前端（用户/角色/部门管理页 + 菜单按钮按权限动态渲染）。
> 排期动机: 排在 P4 之前——P4 监控大盘需要管理员/财务分级可见性；部门实体是 P4 用户长期档案与预算治理的前置；现状存在真实提权漏洞（见 §1）。

## 1. 背景与问题清单（现状审查结论）

| # | 问题 | 严重度 | 现状证据 |
|---|---|---|---|
| 1 | **tenant-service 管理接口零权限校验**：`SysUserController`/`SysRoleController`/`SysTenantController` 的用户增删/角色绑定/角色 CRUD/租户管理只要求登录。普通员工登录后可直接 `POST /api/v1/users` 造 admin 账号（提权） | 🔴 | 三个 Controller 无任何角色判断 |
| 2 | 无统一鉴权执行点：各 Controller 手写 `@RequestHeader("X-User-Roles")` + `FinanceRoles.isFinance()` 字符串解析（agent-core 4 处 Controller + AuditTicketService），新接口默认无校验 | 🟡 | `FinanceRoles` 魔法串 `"admin"/"auditor"` 散落后端 6+ 处、前端 4 处 |
| 3 | 角色变更不生效：角色在登录时烧进 JWT，绑定新角色需重新登录 | 🟡 | `AuthService.login` → `createToken(..., roles)` |
| 4 | 无权限模型：只有角色无权限资源，需求标准①「RBAC **细粒度**权限管理」未满足；需求点名「租户/用户、RBAC 权限管理页面」前端一个都没有 | 🟡 | 无 sys_permission / sys_role_permission 表 |
| 5 | 部门不存在实体（D7 后置项提前）：`expense_reimbursement.dept_name`/`budget.dept_name` 自由字符串（前端文本框随手填），P3c `ToolAccessGuard` 预算越权校验只能做到「租户已知部门」而非「本人部门」 | 🟡 | `budget` 表 uk(tenant_id, **dept_name**, period) |

已有且不动的部分：JWT 签发/解析链、Redis 双机制吊销（jti 黑名单 + 会话版本踢人）、网关防伪造头剥离、MP 多租户拦截器、P3b 可见性统一逻辑（本阶段只换判定依据，不改语义）。

## 2. 已确认决策（2026-08-22）

**决策1 权限粒度：轻量资源级 RBAC（系统管理操作级 + 业务资源级）**
- 建 `sys_permission` 权限资源表（平台级全局目录，**不挂 tenant_id**）+ `sys_role_permission` 映射（租户内）
- 后端按权限码声明式校验（注解 + 拦截器），前端菜单/按钮按权限码动态渲染（路由静态定义 + `meta.perm` 过滤，**不建菜单表**）
- 角色仍是分配单位，业务判定一律改为权限码（`FinanceRoles` 退役）
- **粒度双轨（2026-08-22 补充确认）**：系统管理模块（用户/角色/部门/租户）拆到**操作级**——每接口一码（`user:create`/`user:delete`/`user:assign-role`…），对标开源管理后台按钮级权限标识；业务模块（报销/任务/工单/规则）保持**资源级**——现 3 内置角色无「能看不能删」类配置场景，不过度设计。后续扩目录仅加迁移行

**决策2 角色实时生效：网关查 Redis 快照**
- 登录时把用户权限快照（roles + perms + deptId）写 Redis `finaudit:auth:snapshot:{userId}`
- 网关每请求把现有 2-key `multiGet`（黑名单校验）扩为 **3-key 一次查询**（+snapshot），以快照为权威注入 `X-User-Roles` / `X-User-Perms` / `X-Dept-Id`
- 角色/权限/用户/部门变更时 tenant-service 同步刷新快照 → 下一个请求即生效
- 快照缺失（Redis 异常/冷启动）降级用 JWT 内 roles，perms 置空：无注解业务端点不受影响，`@RequirePerm` 管理端点 fail-closed 返回 403（安全方向正确）

**决策3 部门实体：完整树形**
- `sys_dept` 带 `parent_id`，本期即支持树形 CRUD 与树形选择器交互（为「跨部门分摊」触发规则预留层级语义）
- 用户挂 `dept_id`；`budget` 唯一键迁移为 (tenant_id, **dept_id**, period)；`expense_reimbursement` 增加 `dept_id`，`dept_name` 保留为**提交时快照**（复用语义不变：resubmit 部门只读、审计快照不回改）

## 3. 权限码目录 v1（迁移脚本种子）

**系统管理模块 · 操作级**（每接口一码，菜单码挂 list/manage）：

| 权限码 | 类型 | 说明 | 默认角色 |
|---|---|---|---|
| `user:list` | MENU+API | 用户管理页 + 分页查询 | admin |
| `user:create` / `user:update` / `user:delete` | API | 新增 / 编辑（含密码重置、部门绑定）/ 删除 | admin |
| `user:assign-role` | API | 绑定角色（替换式） | admin |
| `role:list` | MENU+API | 角色管理页 + 列表 | admin |
| `role:create` / `role:update` / `role:delete` | API | 角色增删改 | admin |
| `role:assign-perm` | API | 角色-权限分配 + 权限目录查询 | admin |
| `dept:manage` | MENU | 部门管理页可见 | admin |
| `dept:create` / `dept:update` / `dept:delete` | API | 部门增删改（**树查询不挂码**，见下） | admin |
| `tenant:manage` | API | 租户管理接口组（跨租户管理仍见 §9 边界） | admin |

> ⚠️ **`GET /api/v1/depts` 登录即可、不挂权限码**：部门树是公用数据——报销单创建页的部门选择器普通用户也要读。读开写收：GET 只受登录 + 租户隔离约束，create/update/delete 挂操作级码。

**业务模块 · 资源级**：

| 权限码 | 类型 | 说明 | 默认角色 |
|---|---|---|---|
| `rule:manage` | API+MENU | 财务规则配置（替换现前端 `meta.roles: [admin,auditor]` 与后端 `RuleController` 角色校验） | admin, auditor |
| `reimb:viewAll` | API | 报销单看本租户全量（替换 `FinanceRoles.isFinance` 的 page/detail 分支） | admin, auditor |
| `task:viewAll` | API | 任务列表/详情/步骤看全量 | admin, auditor |
| `audit:viewAll` | API | 审批工单看全量（替换前端审批菜单 `isFinance`） | admin, auditor |
| `audit:approve` | API | 审批动作 approve/reject/terminate/withdraw-agree/refuse | admin, auditor |
| `budget:viewAll` | API | 预算查询放宽到任意部门（`budget_query` 工具越权校验的豁免位） | admin |
| `dashboard:admin` | MENU | P4 管理员风控大盘预留 | admin（P4 启用时生效） |

角色种子映射沿用现有 `admin / user / auditor` 三角色（`finaudit-schema.sql` 已有数据），迁移脚本只补 `sys_role_permission` 行，不动 `sys_role`。

## 4. 鉴权链路（目标态）

```
登录: AuthService.login
  ├─ JWT(userId, tenantId, username, roles)   ← roles 仅作快照缺失时的降级兜底
  └─ Redis SET finaudit:auth:snapshot:{userId} = JSON{roles, perms, deptId, status}   (TTL=token 生命周期上界)

请求: 网关 AuthGlobalFilter
  ├─ 解析 JWT（不变）
  ├─ multiGet(blacklist:{jti}, blackver:{userId}, snapshot:{userId})   ← 一次 Redis 往返
  ├─ 吊销判定（不变）；快照命中 → 快照为权威；未命中 → 降级 JWT roles / perms 空
  └─ 注入 X-Tenant-Id / X-User-Id / X-Username / X-User-Roles / X-User-Perms / X-Dept-Id
     ⚠️ SPOOFABLE_HEADERS 同步增加 X-User-Perms / X-Dept-Id（防伪造，沿用现有剥离机制）

业务服务: common-code 统一组件
  ├─ UserContextFilter: 请求头 → ThreadLocal UserContext{userId, tenantId, username, roles, perms, deptId}
  ├─ @RequirePerm("audit:approve")（支持多码任一命中）+ 拦截器 → 无权限返回 403 R JSON
  └─ Controller/Service 从 UserContextHolder 取身份，删除全部手写 @RequestHeader(X-User-*) 解析

变更刷新: tenant-service 写侧
  ├─ SysUserService: assignRoles / update(角色·部门·状态) / delete → 刷新对应用户快照
  ├─ SysRoleService: 角色权限分配变更 → 反查该角色全部用户（经 SysUserRoleService，实体访问收敛）批量刷新
  └─ 禁用/删除用户: 现有 blackver 踢下线机制不变（快照双保险）

MQ 链路: 快照不进 MQ。工具/编排所需部门一律在 HTTP 提交时落到 reimbursement.dept_id，
        orchestrator 读库内 dept_id/dept_name 快照，无需上下文透传（现状链路不改语义）。
```

## 10. 风险与预案

| 风险 | 预案 |
|---|---|
| `sys_permission` 撞多租户拦截器（SQL 拼 tenant_id 报错） | 迁移前先改 common-mybatisplus-starter 注册 ignore 表 + 集成测试覆盖；R1 内闭环 |
| 网关快照解析拖慢每请求 | 沿用一次 multiGet（3 key）合批；JSON 仅几百字节；Redis 异常降级路径与现有黑名单容错同款 |
| Redis 挂导致管理端大面积 403 | fail-closed 是有意取舍（管理端短暂不可用 vs 越权）；业务端点无注解不受影响 |
| 快照刷新遗漏（改了权限忘刷快照 → 权限残留） | 变更入口收敛：SysUserService / SysRoleService 两个 Service 内统一调 refreshSnapshot；code review 检查项 + 单测覆盖两入口 |
| dept_name 回填脏数据（同名异写建出重复部门） | 迁移脚本 distinct 输出清单人工核对；uk(tenant_id, dept_name) 兜底；回填报告留痕 |
| budget 唯一键切换期间新写入撞旧键 | 迁移放维护窗口单事务执行（本机开发库直接跑）；幂等脚本可重入 |
| resubmit/审计快照语义漂移 | dept_name 列语义明确为「提交时快照」，不回改不重算；dept_id 才是关联键 |
| 前端缓存 perms 过期（改权限后旧菜单残留） | 403 响应触发 `/me` 重拉权限（网关 401/403 拦截器已有类似逻辑可扩展） |
| Feign 内部调用误中权限拦截器 | @RequirePerm opt-in：内部复用端点不挂注解即不受影响；code review 检查 |
